# メンテナンス画面（Cloudflare）

公開サイトを、**サーバーに触れずに**メンテナンス画面へ切り替えます。サイトの前にいるのは Cloudflare なので、
部室PCやコンテナが止まっていても、画面が出ます。**無料プランの機能だけで、お金はかかりません。**

## 仕組み

```
通常      訪問者 ─→ Cloudflare ─→ （Tunnel）─→ 部室PC
メンテ中  訪問者 ─→ Cloudflare ─(リダイレクト)→ メンテナンス画面（Workers の固定ページ）
```

- 切り替えは、**Cloudflare のリダイレクトルール1つの「有効／無効」**です。operator（opsd）が API で切り替えます
- メンテナンス画面は、Workers の**静的ファイル配信**に置いた1枚のページです。**アクセスは無料・無制限**で、
  プログラム（Worker）は置かないので、無料枠の上限（1日10万リクエスト）も関係しません
- お知らせ文と再開予定は、リダイレクト先のURLに付けて渡します（画面側は文字として表示するだけです）
- **管理画面と救出画面は、メンテナンス中も使えます**（切り替えるのは、公開サイトのホスト名だけ）
- 部員向けのページ（動画・マニュアル）も、メンテナンス中は見られません

### できないこと

- **予定しない停止（落ちた・再起動の1〜2秒）には効きません。** その間は、これまでどおり Cloudflare の 502 画面が出ます
  （自動の案内には、Workers のプログラムか有料プランが必要です）
- メンテナンス中は、URL が `…workers.dev` に変わります（画面の「サイトを開く」で戻れます）

## 最初の準備（1回だけ・手作業）

### 1. API トークンを作る

トークンを作るには、別のトークンが必要なので、ここだけは手作業です。

1. Cloudflare のダッシュボード右上のアイコン → **プロフィール → API トークン → トークンを作成**
2. 一番下の「**カスタム トークン**」の「開始する」
3. 名前は「rbs メンテナンス画面」など。**権限を3つ**追加します。

   | 種類 | 項目 | 権限 |
   |---|---|---|
   | アカウント | **Workers スクリプト** | 編集 |
   | ゾーン | **Single Redirect**（「Dynamic URL Redirects」と出ることもあります） | 編集 |
   | ゾーン | **ゾーン** | 読み取り |

4. リソースは、**アカウント**＝自分のアカウント、**ゾーン**＝**このサイトのゾーンだけ**（「特定のゾーン」を選ぶ）
5. 「概要に進む」→「トークンを作成」。表示される文字列を**コピー**する（**この画面を閉じると二度と見られません**）

> 補足：Single Redirect の編集権限は、**そのゾーンのリダイレクトルール全部**に効きます（ルール1つだけには絞れません）。
> `clusters-prj.com` のように、ほかのサービスも載っているゾーンでは、試験のあいだだけにして、終わったらトークンを削除してください。
> 本番の `rbs-kyoto.org` は、このサイト専用なので問題ありません。

### 2. Docker が動いていること

メンテナンス画面のデプロイには `wrangler`（Cloudflare の公式ツール）を使いますが、**Docker の中で動かすので、
Node.js のインストールは要りません。** `install.sh` を終えたPCなら、そのまま使えます。

## セットアップ（コマンド1つ）

```sh
sudo /srv/rbs/repo/deploy/cloudflare/setup.sh
```

聞かれるのは、トークン（入力しても表示されません）と、初めてのときだけ、`workers.dev` のサブドメイン
（メンテナンス画面のURLの一部になります。例：`rbs-kyoto`）です。自動で次のことをします。

| 手順 | 内容 |
|---|---|
| 1 | トークンでゾーンを探す（`PUBLIC_HOST` がサブドメインでも、親のゾーンを探します） |
| 2 | メンテナンス画面を Workers にデプロイし、表示できるか確かめる |
| 3 | 公開サイトを飛ばす**リダイレクトルールを、無効の状態で1つ**足す（**ほかのルールには触れません**） |
| 4 | 切り替えの権限を確かめるため、そのルールを1回更新する（足りなければ、ここでお知らせします） |
| 5 | `/srv/rbs/cloudflare.env`（root だけが読める）を作り、operator を再起動する |

- **何度実行しても壊れません。** ホスト名や画面を直したときは、もう一度実行します。メンテナンス中に実行しても、終わりません
- 公開サイトのホスト名が複数あるとき（`rbs-kyoto.org` と `www.rbs-kyoto.org` など）は、
  `sudo …/setup.sh --hosts rbs-kyoto.org,www.rbs-kyoto.org`
- 保存したトークンを使い回すとき：`--reuse-token`
- 環境変数 `CF_API_TOKEN` に入れておけば、質問なしで実行できます

## 使い方

| やりたいこと | 方法 |
|---|---|
| すぐに始める・終える | 管理画面の「**システムの操作**」→「メンテナンス画面」。お知らせ文（任意）を書いて「メンテナンスを始める」 |
| 日時を予約する | 管理画面の「設定 → **メンテナンス**」。保存すると、自動で反映されます。**Django が止まっても、予約どおりに始まって終わります** |
| 管理画面が開けないとき | **救出画面**（`/rescue/`）の「メンテナンス画面」から、始める・終える |

切り替えは、Cloudflare に反映されるまで、**数秒**かかります。状態（メンテナンス中か、反映に失敗していないか）は、
「システムの操作」と救出画面に出ます。失敗したときは、30秒ごとに自動で再試行します。

### 最初の動作確認（おすすめ）

1. 「システムの操作」で、お知らせ文を入れて「メンテナンスを始める」
2. 数秒待って、**シークレットウィンドウ**で公開サイトを開く → メンテナンス画面になる
3. 管理画面（`admin-…`）は、いつもどおり開ける
4. 「メンテナンスを終える」→ 数秒後、公開サイトが元に戻る

## うまくいかないとき

| 症状 | 原因と対応 |
|---|---|
| `トークンが無効です`（401） | トークンのコピー間違い。作り直して、もう一度 |
| `権限が足りません`（403） | トークンの権限が足りません。上の表の3つを確認（特に Single Redirect の編集） |
| `…を含むゾーンが、このトークンから見つかりません` | トークンの「ゾーン」の対象に、このサイトのゾーンが入っていません |
| デプロイに失敗（`429` や `network`） | Docker Hub の取得制限や通信の失敗です。少し待って、もう一度実行 |
| 「メンテナンス画面をまだ開けませんでした」 | 反映に数分かかることがあります。あとで、表示されたURLを開いて確かめてください |
| 開始しても、公開サイトが変わらない | Cloudflare で、そのホスト名が「プロキシ済み（オレンジの雲）」か確認。ダッシュボードの「ルール → リダイレクト ルール」で、`rbs京都` のルールが有効になっているかも確認 |

## 置き場所を変える・やめる

- メンテナンス画面のURLは、`/srv/rbs/cloudflare.env` の `MAINTENANCE_URL` の1行です。別の無料の置き場所
  （GitHub Pages など）へ移すときは、そこへ同じ `maintenance-page/public/` の中身を置き、この1行を書き換えて、
  `sudo systemctl restart rbs-opsd`（ルールのURLも、次の切り替えで更新されます）
- やめるとき：ダッシュボードで、`rbs京都` のリダイレクトルールと、Workers の `rbs-maintenance` を削除し、
  `/srv/rbs/cloudflare.env` を消して、トークンも削除します

## 安全のために

- トークンは `/srv/rbs/cloudflare.env`（権限 600）にだけ保存し、**コンテナには渡しません**。管理画面（Django）は、
  Cloudflare を直接は操作せず、operator に「依頼」を書くだけです
- operator は、**メンテナンス画面へ飛ばすルール1つの、有効・無効**しか触りません（飛び先のURLは設定ファイルで固定）
- お知らせ文は、URL に入れる前にエンコードし、ルールの式に書式を壊す文字が入らないようにしています
- メンテナンス画面は、戻り先に `config.json` で許可したホストだけを使います。ほかのサイトへ転送される抜け道にはなりません
